NagRaksha
A Parallel-Dispatch Emergency Response & Prevention Platform for Snakebites
Software Requirements Specification (SRS)
Version 1.0
Prepared for Nagathon

Table of Contents
1. Introduction
1.1 Purpose
This document specifies the software requirements for NagRaksha, a cloud-based emergency response and prevention platform for snakebite incidents in India. It is intended for the Nagathon evaluation panel and for the development team as the single reference for scope, features, and constraints. All requirements in this document describe a software system only — no custom hardware, sensors, or physical devices are designed, procured, or built as part of this system. Any physical infrastructure referenced (ambulances, hospitals, antivenom stock) is treated as an existing real-world resource that the software coordinates, not equipment the project manufactures.
1.2 Scope
NagRaksha addresses two connected problems in India's ~58,000 annual snakebite-related deaths: (a) the delay between a bite and qualified treatment, often worsened by a first visit to a traditional healer instead of a hospital, and (b) the lack of a single system that predicts risk, dispatches help in parallel, and coordinates antivenom availability. The system is delivered as a mobile-first application with four distinct interfaces (Public/Victim, Trained Individual, Rescue Team, Ambulance/Hospital) sharing one backend, plus an administrative/analytics layer.
In scope:
SOS-triggered parallel dispatch to trained individuals, snake rescue teams, and ambulance/hospital simultaneously
Role-specific interfaces for the public, trained village-level individuals, rescue teams, ambulance drivers, and hospitals
AI-assisted snake image classification and a conversational myth-busting assistant, both using the user's existing smartphone camera and no added hardware
Weather- and location-based snake-encounter risk scoring using public weather/climate data
Antivenom inventory visibility across hospitals (a software registry, not a physical bank)
Shortest-path routing to the nearest hospital with confirmed antivenom stock
Out of scope (explicitly excluded to keep the system software-only):
Custom motion-sensor or thermal camera hardware for snake detection in the field
A physical venom/non-venom diagnostic test kit
Manufacturing or procurement of ambulances/motorbikes
Manufacturing of antivenom

2. Overall Description
2.1 Product Perspective
NagRaksha is a new, standalone cloud-hosted system. It is not a modification of SARPA, SERPENT, Snakepedia, or The Snakebite Assistant, though it is designed to be aware of the gaps those systems leave open (see Section 6.3). It consumes third-party map/routing and weather APIs and does not require any purpose-built hardware; it runs entirely on the smartphones and computers already owned by its users.
2.2 Product Functions (Summary)
F1 — One-tap SOS that fans out to three responder categories in parallel
F2 — Live location sharing and shortest-path guidance to the incident site
F3 — First-aid capture and symptom logging by the trained individual, shared with the treating doctor
F4 — Rescue-team workflow for safe capture and release
F5 — Ambulance/hospital workflow with antivenom-aware hospital selection
F6 — AI myth-buster chatbot for snake and snakebite questions
F7 — CV-based snake photo identification (using the phone's existing camera)
F8 — Weather- and season-based encounter risk advisory
F9 — Antivenom stock registry and cross-hospital visibility
F10 — Admin/analytics dashboard for coverage planning and funding reporting
2.3 User Classes and Characteristics
2.4 Operating Environment
Client: Android/iOS smartphone application, standard GPS and camera only (no external sensors)
Backend: Cloud-hosted (24/7 availability target, see NFR-1)
Network: Designed to degrade gracefully on 2G/3G rural connectivity; core SOS flow must work on low bandwidth
2.5 Design and Implementation Constraints
No custom hardware of any kind may be introduced; all sensing (location, camera) uses capabilities already built into commodity smartphones
Must integrate with existing government/NGO rescuer directories rather than building a duplicate one from scratch
Must support at least English, Hindi, and one regional language at launch
2.6 Assumptions and Dependencies
Trained individuals and rescue teams are recruited and certified through an external programme (govt/private); the system assumes their existence and provides the software layer to coordinate them
Hospitals voluntarily report antivenom stock levels through the hospital interface or a periodic sync; the system does not independently verify physical stock
Weather/climate data is sourced from a third-party API (e.g., IMD or an equivalent public weather service)

4.3 Software Interfaces

4.4 Communication Interfaces
HTTPS/REST between clients and backend; push notifications for real-time alerts; SMS fallback for the SOS trigger is recommended for low-connectivity areas but is a Should-priority enhancement, not a Day-1 requirement.
5. Non-Functional Requirements
5.1 Permissions
Location — required for SOS accuracy and routing
Contacts — optional, used only if the user opts into an emergency-contact notification feature
Camera — required for snake photo capture (CV classification), user-invoked only, never continuous/background capture
Personal information (name, age, gender) — required only for the responder/hospital handoff, minimized and access-scoped to the active case
6. Appendix
6.1 System Architecture Flow (Reference)
Snake Bite Triggered → SOS sent in parallel to (a) nearby trained individual, (b) nearby rescue team, (c) ambulance/hospital notification → responders reach the affected location → trained individual administers first aid and logs symptoms while the rescue team safely captures/relocates the snake → the ambulance transports the victim to the nearest hospital with confirmed antivenom stock → the symptom log and any identified species are handed to the treating doctor to inform antivenom dosage.
6.2 Village Coverage Model
Trained individuals are intended to cover a configurable radius (default 10 km) across multiple villages, to control programme cost while retaining fast response — this is an operating/business-model assumption the software's routing and coverage-analytics modules are designed to support, not a component the software itself builds.
6.3 Positioning Against Existing Systems
The features below already exist in one or more current apps and are treated as baseline expectations, not differentiators, in this SRS:
Snake species reference guide / photo library (SERPENT, Snakepedia)
Nearest-hospital or nearest-rescuer lookup (SARPA, SERPENT, Snakepedia)
Snake myth/education content (Snakepedia)
Tiered clinical guidance for responders (The Snakebite Assistant)
NagRaksha's distinguishing requirements, reflected above, are:
Simultaneous three-way dispatch (FR-1.2) rather than routing to a single responder type
Antivenom-aware hospital ranking and routing, not just distance (FR-4.2, FR-4.3)
A live, hospital-updatable antivenom registry feeding routing decisions in real time (Module 3.8)
Structured symptom hand-off from first responder to treating doctor (FR-2.3, FR-2.4)
Weather/season-based predictive risk advisory (Module 3.7)
A defined, cost-bounded coverage model for trained individuals across multiple villages (Section 6.2)

NAGRAKSHA
System Design Document
PWA + event-driven emergency coordination architecture
1. Architecture
Use a modular monolith for the hackathon, with clear domain modules and an internal event bus. This is faster and safer to demo than premature microservices while preserving boundaries that can later be split.
2. Logical Flow
PWA → API Gateway/Auth → Incident Service → transactional incident write → Dispatch Orchestrator → three independent dispatch jobs. Each job queries eligible nearby responders/facilities, attempts delivery, records outcome, and schedules escalation. Client state updates through WebSocket/SSE. Hospital routing queries fresh inventory state before ETA ranking.
3. Critical Sequence: SOS
4. Data Model
5. Hospital Ranking
Do not implement raw Dijkstra over the entire road graph inside the hackathon backend unless you already own road-graph data. Use a routing API for travel-time matrices, then implement NagRaksha's decision logic: filter/penalize hospitals by stock freshness and availability, then rank eligible hospitals by ETA. Dijkstra can remain an algorithmic explanation for shortest-path routing, but the product differentiator is the stock-aware decision layer.
6. Offline/PWA Strategy
Cache app shell, translations and medically reviewed static emergency guidance.
Never cache active incident medical data in a shared Cache Storage response.
Queue only safe, explicitly designed mutations; an SOS itself must show Pending until the server acknowledges it.
Lazy-load maps, analytics and AI modules so the emergency shell starts first.
Web Push is an enhancement, not the only dispatch transport. iOS/iPadOS Web Push requires a Home Screen web app on supported versions.
7. Security and Abuse Controls
RBAC: victim, responder, rescue, ambulance, hospital, admin.
Hospital inventory updates require authenticated hospital role and audit trail.
Rate-limit SOS creation per device/account while preserving an emergency override path.
Signed object URLs for photos; strip metadata where practical.
Do not expose responder personal details broadly; share only what an active incident needs.
Use synthetic demo data during judging.
8. Deployment
Hackathon: one frontend deployment + one API deployment + managed PostgreSQL. Add Redis/worker only if parallel jobs or presence require it. Production evolution: multi-AZ database, durable queue, independent dispatch workers, monitoring, backup/restore, regional failover, directory integrations and formal clinical/content governance.
Layer | Components
Client | React/TypeScript PWA; role-based routes; service worker; IndexedDB for non-sensitive queued UI state; responsive hospital/admin console.
API | REST endpoints plus WebSocket/SSE for live incident state. Authentication and role authorization at API boundary.
Core domains | Incident, Dispatch, Responder, Hospital/Inventory, Routing, Clinical Handoff, Notification, Content/AI, Analytics.
Data | PostgreSQL + PostGIS for incidents, users, facilities and geospatial queries; Redis optional for presence, locks, rate limits and short-lived dispatch state.
Async | Job queue/event worker for fan-out, retries, escalation and notification delivery.
External | Maps/routing provider, weather API, Web Push provider/browser push services, optional SMS gateway, object storage for snake photos.
Step | Action | Failure behavior
1 | Client obtains best available foreground location. | If denied, allow manual location/pin; do not block UI indefinitely.
2 | POST /incidents with idempotency key. | Retry safely; same key returns same incident.
3 | Database commits incident. | Only after commit return accepted incident ID.
4 | Outbox/event emits IncidentCreated. | Worker retries until processed.
5 | Dispatch jobs start independently for trained responder, rescue team and ambulance/hospital. | One branch failure cannot block others.
6 | Delivery attempts are recorded. | Timeout expands search radius / next candidate.
7 | Acceptance uses atomic compare-and-set. | Prevents two responders claiming one exclusive slot.
8 | State event reaches victim UI. | Reconnect fetches canonical server state.

NAGRAKSHA
Brand Style Guide
Calm urgency. Clinical clarity. Rural accessibility.
1. Brand Position
NagRaksha should look like emergency infrastructure, not a wildlife app. The visual system must communicate urgency without panic and medical credibility without looking bureaucratic.
2. Visual Identity
3. Typography
4. Logo Direction
Wordmark: “NagRaksha”. Symbol direction: a minimal protective shield/path motif with a subtle snake curve. Avoid aggressive cobra-head mascots, medical crosses used as decoration, and detailed wildlife illustration. The product is about protection and routing.
5. Component Rules
SOS button: Emergency Red, largest control on victim home, text label always present.
